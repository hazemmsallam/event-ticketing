00 Design tenets

Five rules the rest of the document derives from.

  1. The database is the arbiter of inventory. The cache is an accelerator. Redis may say a seat is free and be wrong; the database must never be wrong. Every hold is validated by a uniqueness constraint inside the transaction that writes it.
  2. Holds are leases, not locks. A hold carries a wall-clock expiry in its row. Correctness must not depend on a background job running on time — expiry is evaluated on read, and the sweeper is only a garbage collector.
  3. Never hold a database transaction across a network call. Payment splits into short transactions with the gateway call in the gap.
  4. Every in-doubt state must be resolvable by a reconciler. If a process dies between “charged” and “confirmed”, a job must finish or reverse it.
  5. Money and inventory reconcile independently. A charge that cannot be honoured is refunded, never silently dropped.

01 System architecture

Read traffic and write traffic take deliberately different routes: search is served from cache and replicas and may be seconds stale, while every hold and confirmation goes to the primary.

  • API Gateway — authn/z, rate limiting per user and per trip, and client-supplied idempotency keys on every mutating call. Seat-hold endpoints are the hottest abuse target.
  • Search — pure read path, served from cache falling back to read replicas. Never touches the primary.
  • Reservation — the only writer of hold state. Redis advisory lock first, authoritative DB write second.
  • Payment Orchestrator — a separate service so its transaction boundaries are real; inlining it collapses two transactions into one via self-invocation.
  • Sweeper / Reconciler — idempotent safety nets, both leader-elected so N replicas don’t stampede.

02 Domain model

Modelling calls worth defending

  • SEAT vs SEAT_INVENTORY. SEAT is physical (coach 3, seat 12A) and static. SEAT_INVENTORY is that seat on that trip, and is what gets sold. Without the split you cannot price the same physical seat differently across dates.
  • TICKET snapshots the seat label at issue time. Layouts get remapped; an issued ticket must never change retroactively.
  • RESERVATION_SEAT.active_lock is the keystone — see §05.

03 Seat lifecycle

  • HELD and BOOKED are the only states that occupy inventory — the uniqueness constraint keys off exactly this pair.
  • Expiry is lazy-evaluated. A HELD row past expires_at is treated as free on the next read of that trip and released in the same transaction as the new hold.
  • RELEASED is terminal for that row, not a return to HELD. Re-holding writes a new row, preserving an append-only audit trail.
  • BLOCKED lets operations withhold seats without inventing a fake reservation.

04 Flow A · Seat hold & lock acquisition

Two layers, one authority

LayerMechanismPurposeAuthoritative
RedisSET NX PX in LuaReject ~99% of collisions in <1 msNo
DatabaseUNIQUE on generated columnGuarantee no double-booking, everYes

Seat selection is all-or-nothing — a party of three won’t accept two seats. SET NX is not atomic across keys, so acquisition must be scripted. Redis runs scripts single-threaded, closing the check-and-set window.

-- KEYS[1..N] = seat:{tripId}:{seatId}   ARGV[1] = token   ARGV[2] = ttl ms
for i = 1, #KEYS do
  if redis.call('EXISTS', KEYS[i]) == 1 then
    return 0                      -- someone holds one: take nothing
  end
end
for i = 1, #KEYS do
  redis.call('SET', KEYS[i], ARGV[1], 'PX', tonumber(ARGV[2]))
end
return 1
Two non-obvious correctness details

Flush ordering. Releasing expired holds is an UPDATE; taking the new hold is an INSERT. ORMs commonly order INSERTs before UPDATEs within a flush — so the insert collides with the row you were about to free. Force a flush between them.

Deterministic seat ordering. Sort seat IDs before inserting. Two requests acquiring {A,B} and {B,A} take index locks in opposite order and deadlock. A global order turns a deadlock into a clean wait-then-conflict.

05 The uniqueness guard

Partial indexes (WHERE status IN (…)) don’t exist in MySQL. A generated column plus NULL semantics reproduces them:

active_lock VARCHAR(48) GENERATED ALWAYS AS (
    CASE WHEN status IN ('HELD','BOOKED')
         THEN CONCAT(trip_id, '-', seat_inventory_id)
         ELSE NULL END
) STORED,
CONSTRAINT uq_reservation_seat_active UNIQUE (active_lock)
  • Occupied rows produce a non-null key → any second occupant violates the constraint.
  • Released rows produce NULL, and SQL permits unlimited NULLs in a unique index → seats recycle freely.
  • Correctness holds even if the application is bypassed — admin scripts, migrations, a second service.
Operational warning — learned the hard way

An ORM with schema auto-generation (ddl-auto: update / create) will recreate this table from the entity classes — and it cannot see a generated column, because it isn’t a mapped field. The column and its unique index vanish silently. Every code path still looks correct; the conflict handler simply becomes dead code, and double-booking becomes possible.

Pin schema management to migrations only (validate), and add a test that asserts the constraint exists in the deployed database.

06 Flow B · Payment & persistence

  • A gateway call takes seconds. Holding a transaction across it pins connections until the pool starves.
  • The INITIATED row is the durable record of intent. If the process dies after it, the reconciler queries the gateway by idempotency key and finishes the job.
  • The rollback on “hold expired” is deliberate — it preserves INITIATED so the reconciler refunds. Making this path “not throw” would strand real charges.
  • Ticket generation must be idempotent; reconciliation can confirm the same reservation twice.
  • Evict, don’t write-through, and register it after commit — otherwise a concurrent reader repopulates the cache from pre-commit state.

07 Flow C · Expiration & cleanup

PathTriggerRole
Redis TTLkey expiryFrees the advisory lock only
Lazy releasenext hold on that tripPrimary — hot inventory recycles instantly
SweeperscheduledSafety net for trips nobody is browsing

Sweeper requirements: bounded batches (~200) so a flash-sale expiry wave can’t pull tens of thousands of rows into one transaction; FOR UPDATE SKIP LOCKED so workers make progress instead of queueing; a lease or leader election so replicas don’t duplicate work; and a cap on iterations per tick.

Invariant

The sweeper going down must degrade performance, never correctness. Lazy release is what guarantees that.

Why the seat-map TTL is seconds, not minutes

A stale seat map can never cause a double-booking — the constraint stops that. It only causes a user to click a seat that’s gone and get a 409. Seconds keeps that rare without hammering the primary.

Concurrency strategy by contention shape

Lock at the narrowest correct scope. If capacity is per coach class, lock the class quota row, not the trip. Locking the trip serialises every sale on it — including classes that never contend. This is the single most common throughput mistake in this design.

10 Pre-ship checklist

  • uq_*_active unique index exists in the deployed database — asserted by an automated test, not by inspection
  • Schema tooling is migrations-only; auto-DDL disabled in every environment
  • Seat IDs sorted before insert (deadlock avoidance)
  • Flush forced between expiry-release and new-hold insert
  • Payment split across two transactions, gateway call in the gap
  • Ticket generation idempotent
  • Cache eviction registered after commit
  • Sweeper batched, SKIP LOCKED, leader-elected
  • Cache TTLs jittered
  • Duplicate-pay returns 409, not 500
  • A refund path returns BOOKED seats to the pool and clears any sold-out flag
