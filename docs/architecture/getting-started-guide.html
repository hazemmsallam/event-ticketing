1 What we're building

A system that sells tickets to events. Someone opens an app, picks a concert, chooses where they want to sit, pays, and receives a ticket.

That sounds simple, and for one customer it is. It becomes hard when thousands of people want the same seats at the same second and real money is involved. Almost every design decision in this codebase exists because of that sentence.

There are two applications:

ApplicationWho uses itWhat it does
event‑ticketingCustomers, via the mobile app The main API. Owns the database. All the rules live here.
adminVenue staff A web back-office for drawing halls and creating events. Stores nothing itself — it calls the API.
Key idea

The admin app has no database of its own. If it did, we would have two copies of the rules that could disagree. One owner of the data means one version of the truth.

3 Why rooms and shows are separate

A beginner might store “seat A5 costs 50” and be done. We deliberately don't. Here's why.

Think of it like

A cinema screen exists all year. Films come and go. The room doesn't change when the film changes — but the price absolutely does. A blockbuster on Saturday night costs more than a Tuesday matinée, in the exact same seat.

So we split them:

  • The hall describes the room — where the seats are, what shape the sections are. It rarely changes.
  • The event describes one show — the date, and the price of every section.
Key idea

A section has no price of its own. Prices live on the event. If you look for a price field on Section, you won't find one — that's intentional, not an oversight. An event cannot be published until every section has been given a price.

Sections are shapes, not labels

A section isn't just the word “Balcony”. It's an actual shape drawn on a map — stored as a list of corner points. Staff draw it in the admin editor: a rectangle, a circle, a curve, or any free-form outline.

The system then works out which seats are inside that shape, mathematically. Staff never have to say “seats A1 through A20 belong to the Balcony” — they draw a shape around them and the computer figures it out.

5 The hardest problem: two people, one seat

Imagine Sara in Amman and Omar in Dubai. Both are looking at seat A5. Both screens say “available”. Both tap Book at the same instant.

The trap is that the code looks perfectly correct. “Check if free, then book” is exactly what you'd write. It works every time you test it by hand. It fails only when two requests overlap by a few milliseconds — which, on a busy on-sale, is constantly.

Remember this

You can never fix a race condition by checking more carefully in your code. Between your check and your save, the world can change. The fix has to come from somewhere that can decide atomically — in one indivisible step.

6 How we actually solve it

We let the database be the referee, because it is the one place that can make a decision no one can interrupt.

Think of it like

A bouncer with a guest list. Two people can both believe they're on the list, but only one can physically get through the door. The bouncer doesn't care how fast they run or how convinced they are.

We gave the database one unbreakable rule:

The rule

No two active bookings may name the same seat at the same event.

Now when Sara and Omar both try, the database accepts the first and physically refuses the second. Our code catches that refusal and tells Omar “sorry, just taken”. Both are treated fairly, and the seat is sold exactly once.

The word active is doing real work. A booking is active while it is being held or has been paid for. Once it's cancelled or expired, it stops being active — and the seat becomes bookable again, automatically.

Important for newcomers

Our Java code also checks whether a seat is taken before saving. That check exists only to produce a friendly message naming the seats. It is not what keeps the system correct. If you ever remove the database rule because “the code already checks”, you will silently start selling seats twice.

What about general admission?

Standing tickets have no identity — there's no “ticket number 37” to make unique. The rule instead is “the total sold must not exceed capacity”, which no single-row rule can express.

So for those, we do something different: we make everyone queue for a moment. One booking at a time is allowed to count the tickets already sold and add its own. It's slower, but for a counter there is no faster safe option.

7 Why holds exist

When you pick a seat, we don't sell it to you — you haven't paid yet. But we can't leave it available either, or someone takes it while you're typing your card number.

So we set it aside temporarily. That's a hold, and it lasts 10 minutes.

Think of it like

A taxi you've booked but not yet got into. It's not yours forever — if you don't show up, the driver leaves and takes another fare.

Who gives the seat back?

Two things do, and having both is deliberate:

  1. The next customer. When anyone tries to book that same event, we first sweep up any holds that have run out. Popular events clean themselves up constantly, for free.
  2. A background job. Every 30 seconds, a job tidies up holds for events nobody is looking at.
Key idea

A hold's expiry time is written on the booking itself. So a hold is expired the moment its time passes — not when some job gets round to noticing. If the background job broke and stopped forever, the system would still be correct; it would just leave tidy-up work undone on quiet events.

8 Taking payment safely

Charging a card means talking to an outside company, over the internet, and that can take a few seconds. A few seconds is an eternity for a database.

So we deliberately split payment into three steps:

Why bother? Because a database has a limited number of connections. If every customer paying held one open while waiting for a bank, a busy moment would use them all up and nobody could do anything — not even browse.

The question that shapes everything

Ask yourself: what if the server loses power between steps 2 and 3?

The customer's card is charged. Our database has no record of it. Without a plan, that money vanishes into a gap.

This is exactly why step 1 exists. Before we charge anyone, we write down “we are about to charge this person”. That note survives a crash. A background job then checks every unfinished note against the payment company:

What the payment company saysWhat we do
No charge was madeMark it failed. Nothing was taken.
Charged, and the seats are still heldFinish the booking. Send the tickets.
Charged, but the hold ran outRefund the customer automatically.

Charging twice by accident

If we retry a charge after a timeout, could we take money twice? No — every charge carries a unique code.

Think of it like

A receipt number. If you hand the same receipt number to the cashier again, they say “I've already done this one” instead of charging you a second time.

One subtlety worth understanding, because it caused a real bug: that code must change when the customer genuinely tries again with a different card. Otherwise the payment company helpfully replays the old refusal, and the customer can never pay. So the code includes an attempt number: booking-42-1, then booking-42-2.

9 When things break

Real systems fail. Servers restart, networks drop, banks time out. The design assumes this rather than hoping otherwise.

The promise we make

We never keep someone's money without giving them their seats, and we never give away seats we haven't been paid for. Every failure resolves to one or the other.

The tool that makes this work is that “about to charge” note. As long as it exists, we know something is unfinished, and a job keeps working on it until it's resolved.

When a problem can't be solved automatically

Occasionally something can't be resolved — a refund keeps being rejected, or our credentials for the payment company expired. Retrying forever would be pointless and would slow down every other payment waiting behind it.

So after several attempts, spaced further and further apart, we park it for a human and stop retrying. Staff get a list showing the amount, the customer, and the reference number to search for at the payment company.

This is called a dead letter — a message nobody could deliver, set aside for a person to handle instead of thrown away.

10 Making it fast

When tickets go on sale, far more people are looking than buying. Thousands refresh the seat map; a handful actually book.

Asking the database to redraw the whole seat map for every viewer would exhaust it. So we keep a ready-made copy in a fast store called Redis, and serve most viewers from that copy.

Think of it like

A photocopy of a noticeboard by the entrance, so a hundred people don't crowd around the original.

The copy is kept for only a couple of seconds — long enough to absorb the crowd, short enough that nobody stares at badly out-of-date information.

Why a stale copy is safe

Worst case, someone taps a seat that has just gone and is told “sorry, taken”. Slightly annoying — but never wrong, because buying still goes through the database and its unbreakable rule. The copy only affects what people see, never what they get.

One refinement worth knowing: we make each copy expire at a slightly random time. If every copy expired at the same instant, all those viewers would hit the database together — the stampede we were trying to avoid, arriving on a schedule.

11 Stopping people gaming the system

If holding a seat is free and easy, someone will hold every seat in the venue and sell none of them — a way to sabotage an on-sale, or to hoard tickets. Four limits work together:

  1. You must say who you are. Identity comes from a login token, never from something the app can type in. You cannot limit a person you cannot recognise.
  2. At most 10 seats per request. So one request can't lock a whole venue.
  3. One live hold at a time. Finish or cancel before starting another.
  4. A limit on holds you don't pay for. Paying clears your record instantly, so genuine buyers are never slowed down. Only people who repeatedly take seats off sale and never buy get blocked.
Why the fourth one is designed that way

A naive limit like “5 bookings per minute” punishes the wrong person: a decisive buyer looks identical to a hoarder. Counting unpaid holds instead targets the behaviour we actually object to — taking inventory off sale and never buying it.

12 Glossary

TermIn plain words
Race conditionTwo operations overlapping, where the result depends on who happens to finish first
AtomicHappens completely or not at all — nothing can interrupt halfway
TransactionA group of database changes that all succeed together or are all undone
RollbackUndoing a transaction, as if it never happened
ConstraintA rule the database itself enforces and will not let you break
LockMaking others wait so only one operation touches something at a time
HoldA seat set aside temporarily while a customer pays
ExpiryThe moment a hold stops counting and the seat returns to sale
IdempotentSafe to repeat — doing it twice has the same effect as once
ReconciliationChecking our records against the payment company's and fixing differences
Dead letterSomething that couldn't be processed, set aside for a human
CacheA fast temporary copy, to avoid repeating slow work
MigrationA numbered script that changes the database structure

Before you change anything

If a piece of code looks strangely complicated, assume it's solving a problem you haven't hit yet — especially around payments and holds. Read the comment above it first. Most of the odd-looking parts exist because of a specific failure that already happened once.

The three ideas to take away

1. Correctness lives in the database, not in the code.
2. Never hold a database transaction open while waiting for the outside world.
3. Assume every step can fail, and make sure something can always finish the job.
