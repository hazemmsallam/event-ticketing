00 How to read this

Each block below is described the same way, so you can scan for what you need:

FieldAnswers
DoesIts one responsibility
NeedsWhat it is given at construction, plus any infrastructure it cannot work without
Used byWho calls it — change it and these are affected
WatchThe non-obvious thing that breaks if you change it carelessly

Every dependency listed was read from the class's constructor, so it reflects the code rather than an intention.

01 What the application needs to run

DependencyRequired?Used forIf missing
MySQL 8Yes All data; the uniqueness rule that prevents double-booking Application will not start
RedisDegraded Read cache, rate limits, scheduler leases Runs, but every read hits the database and limits stop applying
JDK 21+YesRecords, pattern switches, text blocksWill not compile
Payment providerStubbedCharging, refunds, lookups Currently FakePaymentGateway always approves
Schema ownership

Flyway owns the schema; Hibernate must stay on ddl-auto: validate. With update or create, Hibernate rebuilds tables from the entity classes and cannot see the generated active_lock column — silently deleting the double-booking guard. SchemaGuardIntegrationTest exists to catch this.

This is a stub, not authentication. No signature or expiry is checked. 05 Reservation core — reservation.service

ReservationServicethe centre of the system
Does
Holds, seat swaps, cancellation, expiry, availability reads, payment state transitions, reconciliation decisions
Needs
BookingRepository · BookingSeatRepository · PaymentRepository · EventRepository · SeatRepository · SectionRepository · TicketRepository · ReservationProperties · Clock · CacheManager · ObjectMapper · UnpaidHoldThrottle
Used by
BookingController · EventBrowseController · PaymentService · both jobs · PaymentReviewController
Watch
Four invariants live here — see below. It is large because the booking transaction genuinely spans these concerns; splitting it would move logic across transaction boundaries.

The four things not to break

RuleWhy
Flush between releasing expired holds and inserting a new one Hibernate orders inserts before updates in one flush, so without it the insert collides with the row being freed
Sort seat ids before insert Two overlapping requests taking locks in opposite order deadlock
Evict caches after commit Evicting inline lets a concurrent reader repopulate from uncommitted state
The pre-check is cosmetic The unique index resolves races. The Java check only produces a friendlier message

Clock is injected rather than read from Instant.now() so tests can control time — and so every replica shares the database's timeline (§10).

06 Payment — payment, reservation.service

PaymentGatewayinterface — the provider seam
Does
charge · lookup · refund
Needs
nothing — implementations bring their own
Watch
Two known gaps before a real provider: no currency parameter, and refund returns void so a failed or asynchronous refund cannot be represented.
FakePaymentGatewaydevelopment stand-in
Does
Always approves; keeps an in-memory ledger so lookups work
Watch
The ledger is per instance, so multi-instance reconciliation cannot be tested with it. It also never declines, which hides retry bugs.
PaymentServiceorchestrates the three steps
Does
begin → charge → record reference → apply outcome
Needs
ReservationService · PaymentGateway
Watch
Must stay a separate bean. It calls ReservationService across a bean boundary, which is what makes those @Transactional steps real transactions. Inlining it into ReservationService would collapse them into one via self-invocation and hold a transaction open across the network call.
The throw is the mechanism

When a charge succeeds but the hold has lapsed, applyPaymentResult throws on purpose. The rollback preserves the INITIATED row so reconciliation can refund. "Handling it gracefully" instead would mark the payment resolved and strand a real charge.

Supporting records: PaymentContext (snapshot passed out of transaction one), PaymentResult, PaymentSummary, ReconcileOutcome, PaymentReviewItem. All immutable, none touch the database.

07 Background jobs

HoldSweeperreturns abandoned seats to sale
Does
Releases expired holds in batches of 200, up to 20 batches per tick
Needs
ReservationService · SchedulerLease · ReservationProperties · Redis (lease)
Watch
It is a safety net, not the mechanism. Booking-time lazy release handles busy events. If this job stopped, the system stays correct.
PaymentReconciliationJobresolves in-doubt payments
Does
Asks the provider what happened, then confirms, fails, or refunds; records failures with backoff and dead-letters after 6
Needs
ReservationService · PaymentGateway · SchedulerLease · ReservationProperties
Watch
Provider calls happen outside the transaction, which is why reconcile returns a refund instruction rather than performing it. Refunds are claimed in the database first, so overlapping runs cannot refund twice.
SchedulerLeaseone instance per tick
Does
SET key owner NX PX ttl — atomic in Redis
Needs
StringRedisTemplate
Watch
Never renewed or released early — it simply expires, so a dead worker blocks a job for at most one interval. Fails open; it is an optimisation, and the database claim is the real guarantee.

11 Errors — common.exception

Throw the exception that carries the right status; the handler does the rest. Never build an error response in a controller.

ExceptionStatusThrow when
BusinessRuleException400The request is valid but the rules forbid it
UnauthorizedException401No usable credential
ResourceNotFoundException404Missing — or not the caller's, so ids can't be probed
ConflictException409Someone else won, or work is already in flight
TooManyRequestsException429Throttled; carries Retry-After

GlobalExceptionHandler maps all of these to the shared ApiError shape and is the only place that sets response status for errors.

13 Dependency rules

Four rules keep the structure from eroding. Each has a concrete failure behind it.

RuleBecause
Controllers hold no business logic Rules would then differ per entry point, and background jobs bypass controllers entirely
Services never call other services' repositories Ownership of a table stays with one service, so its invariants are enforced in one place
Never call a network service inside a transaction Connections are finite; a slow provider becomes a total outage
Correctness rules go in the schema, not the service Application checks cannot survive concurrency; database constraints can
Before changing a block

Check its Watch row first. Most of them record a failure that has already happened once — the flush ordering, the seat sorting, the payment bean boundary, and the schema guard were all written after something broke.
