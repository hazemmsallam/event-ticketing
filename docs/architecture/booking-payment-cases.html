00 How to read this

A purchase crosses two systems that can fail independently: inventory (the database) and money (the payment provider). Every interesting case in this document is a disagreement between them.

InventoryMoneyMeaningResolution
HeldNot chargedNormal pending statePay, cancel, or expire
HeldChargedConfirm itBooking becomes CONFIRMED
GoneChargedThe dangerous oneAutomatic refund
HeldUnknownIn doubt after a crashReconciliation resolves

Two design rules make all of this recoverable, and every case below depends on them:

  • A durable record of intent exists before any money moves. The Payment row is written as INITIATED and committed before the gateway is called, so a charge can always be traced back to something.
  • No database transaction is open during the charge. The process may die at any instant without holding locks — and whatever it was doing is reconstructable.

01 Creating a hold — guards & routing

Seven guards run before any inventory is touched. They are ordered cheapest-first, so an abusive request is rejected without ever reaching the database.

Routing is by request, not by hall

A hall can mix seated and general-admission sections in the same room, so the decision is made from what the client asked for — not from hall.isSeated.

02 Seated holds

The pre-check is cosmetic — the index decides

Two customers can both pass the “already held?” pre-check. The unique index on the generated active_lock column is what actually resolves the race, and the loser surfaces as case 6 rather than an overselling bug. Removing the pre-check would change only the quality of the error message, not the correctness.

05 Payment — the happy path

Why the reference gets its own transaction

applyPaymentResult deliberately rolls back when the hold has lapsed. A reference written inside it would be discarded in exactly the case where reconciliation needs it to issue a refund — so it is committed separately, first.

Case 34 deserves the right wording in the UI

A 409 here means “we may already hold a charge for you and are still confirming it”. Retrying is refused on purpose: issuing a new idempotency key while the previous attempt is unresolved would orphan a charge the gateway may already have taken. Present it as “payment processing — check back shortly”, never as a failure.

Retry after a genuine decline

A FAILED payment can be retried, and the attempt counter advances so the gateway issues a real second charge rather than replaying the stored decline:

These are the cases the architecture exists for: the process, network, or database fails while a charge is in flight.

Why nothing is lost

Every window leaves the payment row INITIATED. That single state means “a charge may exist that we have not accounted for”, and it is the reconciler's entire work queue.

08 Charged, but the seats are gone

The case worth understanding in full: the customer's card was charged, and between starting payment and finishing it their hold expired — or the seats were released and resold.

The throw is the mechanism, not a bug

Rolling back is what preserves INITIATED so the reconciler can see the payment and refund it. A well-meaning change that “handles the error gracefully” instead of throwing would mark the payment resolved and strand a real charge — the customer's money kept, with no seats and no refund.

The seats are never double-sold in this scenario: they were released by expiry and legitimately resold. Inventory stays correct; only the money needs unwinding, which is why a refund — not a seat clawback — is the right compensation.

09 Reconciliation

Runs every 30 seconds over payments left INITIATED for more than a minute. The gateway lookup happens outside the transaction, and refunds are returned as an instruction to the job rather than performed inside it.

#Gateway saysBooking isAction
40No charge / failedanyFAILED — nothing was taken
41ChargedCONFIRMEDMark SUCCEEDED; the normal path already won
42ChargedPENDING, still validConfirm the booking — crash recovery
43ChargedEXPIRED / CANCELLEDRefund

Confirmation is idempotent throughout: ticket generation no-ops when tickets exist, so a booking confirmed twice by two runs still issues exactly one set.

11 Guarantees & known gaps

What the system guarantees

  • A seat is never sold twice. Enforced by a unique index, not by application logic.
  • A charge is never silently lost. Every failure leaves a durable INITIATED row for the reconciler.
  • Money is never kept without seats. A charge that cannot be honoured is refunded.
  • Abandoned holds always return to sale, via lazy release or the sweeper.
  • Confirmation is idempotent, so recovery can run repeatedly without side effects.

Known gaps

Carry these into planning

No refund path after confirmation. CONFIRMED is terminal: cancelling is rejected, seats cannot be returned to the pool, and an event marked SOLD_OUT never returns to PUBLISHED.

Reconciliation has no dead letter. A payment that keeps failing to reconcile retries forever, logging each time, with no alert and no manual-review state.

Refunds are assumed synchronous and successful. The gateway contract returns void, so a refund that fails or settles asynchronously is recorded as done.

Charging assumes a terminal answer inline. Real 3-D Secure needs a webhook and an intermediate “authentication required” state, which does not exist yet.
