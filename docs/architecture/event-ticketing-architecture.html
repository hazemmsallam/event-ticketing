00 What this is

An event ticketing platform where a venue is modelled as a hall containing freely-drawn sections, and each event sells that hall’s inventory at its own prices. A single hall can mix reserved seating and standing-room capacity in the same room.

ApplicationPortRole
event-ticketing8082Core REST API — catalog, inventory, bookings, payments, tickets. Owns the database.
admin8092Thymeleaf back-office. Holds no database; calls the API over HTTP and renders the visual hall editor.

Design tenets

  • The database is the arbiter of inventory. Service-layer checks exist to produce friendly errors; a unique index is what actually prevents double-booking.
  • Holds are leases. expires_at lives on the row and is evaluated on read. The sweeper is a garbage collector, not the mechanism.
  • No transaction spans a network call. Payment is two short transactions with the gateway call in the gap.
  • Prices belong to events, not venues. A hall describes a room; the same section is worth different amounts at different events.
  • Flyway owns the schema. Hibernate is validate only.

01 System topology

  • The admin app owns no data. Every mutation is an HTTP call to the API, which keeps one set of business rules rather than two.
  • PaymentService calls ReservationService across bean boundaries — that is what makes the two @Transactional proxies real. Merging them would silently collapse both transactions into one via self-invocation.
  • PaymentGateway is an interface; FakePaymentGateway is the dev implementation. Swapping in a real PSP touches nothing else.

02 Domain model

Decisions worth defending

  • Sections are geometry, not labels. SECTION.points is a JSON polygon in the hall’s layout-pixel space. Seats are assigned to a section by point-in-polygon containment, so any shape — circle, triangle, curve, free-form — works without a shape-specific schema.
  • Sections carry no price. Price lives only in EVENT_PRICING, one row per (event, section). A hall describes a venue; the same section is worth different amounts at different events. Publishing an event requires a price line for every section.
  • BOOKING_SEAT snapshots section_name and currency at sale time, so re-drawing a hall never rewrites history.
  • LAYOUT_PRESET is hall-agnostic — its members are stored as one JSON document with bounding-box-relative coordinates, so a saved block stamps into any hall.
Removed on purpose

SeatType (VIP / PREMIUM / REGULAR) was deleted in V8. Once a section owns name, price, capacity and booking mode, seat type was a weaker second classification competing with it — it could not express “Royal” vs “Balcony Left”, and pricing had two rival keys.

03 Three booking modes

ReservationService.createBooking routes on the request shape, not the hall type, because one hall can mix seated and general-admission sections in the same room.

Request containsPathCapacity authorityConcurrency control
seatIdsbookSeatsPer-seat uniquenessOptimistic — DB unique index
sectionId + quantitybookGeneralAdmissionSectionsection.capacityPessimistic — lock the section row
neither, non-seated hallbookGeneralAdmissionevent.max_capacityPessimistic — lock the event row

Seated booking is lock-free and scales horizontally: conflicts surface as a unique-index violation translated to 409. General admission has no per-unit identity, so capacity must be counted — capacity − confirmed − reserved — under a row lock.

Lock at the narrowest correct scope

Section-based GA locks the section, not the event. Locking the event would serialise every GA sale for that event — including sections with entirely independent capacity. This was corrected after review; the legacy whole-event path still locks the event because its capacity genuinely is event-wide.

Expiry is lazy-evaluated. A PENDING_PAYMENT booking past expires_at is treated as free by the next booking on that event and released in the same transaction. Correctness never depends on the sweeper having run.

05 Hold acquisition under contention

  • The pre-check is cosmetic. findForSeats exists only to name the taken seats in a friendly message. Both customers can pass it; the index is what resolves the race.
  • Flush ordering is load-bearing. Releasing expired holds is an UPDATE; taking the new hold is an INSERT. Hibernate orders INSERTs first within a flush, so without the explicit flush() the insert collides with the row being freed.
  • Seats are sorted by id before insert so two overlapping requests can’t take index locks in opposite order and deadlock.

06 The double-booking guard

MySQL has no partial indexes. A generated column plus NULL semantics reproduces one — defined in V2__reservation_schema.sql:

active_lock VARCHAR(48) GENERATED ALWAYS AS (
    CASE WHEN status IN ('HELD', 'BOOKED')
         THEN CONCAT(event_id, '-', seat_id)
         ELSE NULL END
) STORED,
CONSTRAINT uq_booking_seat_active UNIQUE (active_lock)
  • Occupied rows produce a key like 5-A2 → a second occupant violates the constraint.
  • RELEASED rows produce NULL, and MySQL permits unlimited NULLs in a unique index → seats recycle freely and history stays append-only.
  • Correctness survives even if the application is bypassed — scripts, migrations, a second service.
This has already failed once — verify it

Hibernate ddl-auto: update/create recreates booking_seat from the entity class, and it cannot see a generated column because it is not a mapped field. The column and its unique index vanish silently: every code path still looks correct, but the conflict handler becomes dead code and double-booking becomes possible.

This happened in this project and was found by comparing the live schema against the migration — not by reading code. ddl-auto is now validate, and SchemaGuardIntegrationTest asserts the column, its uniqueness, and that status is still varchar rather than a Hibernate-generated enum.

07 Payment

  • The INITIATED row is the durable record of intent. If the process dies after it, PaymentReconciliationJob queries the gateway by idempotency key and finishes or refunds.
  • The throw is the recovery mechanism. When the hold expired mid-charge, rolling back preserves INITIATED so reconciliation can refund. “Helpfully” not throwing would strand real charges.
  • generateTickets is idempotent — reconciliation may confirm the same booking twice.
  • Concurrent pay() calls: the unique booking_id lets one through; the loser now gets 409 rather than a 500.
Known gap

maybeMarkSoldOut is one-way. Nothing moves an event from SOLD_OUT back to PUBLISHED, and cancelBooking rejects anything not PENDING_PAYMENT — so there is currently no refund-after-confirmation path returning seats to the pool.

08 Expiry & cleanup

Lazy release is the primary mechanism — hot events recycle inventory instantly. The sweeper only matters for events nobody is browsing, and works in 200-row batches capped at 20 batches per tick so a flash-sale expiry wave can’t lock thousands of rows in one transaction.

Invariant

The sweeper going down degrades performance, never correctness.

09 Caching

CacheKeyTTLPattern
eventSeatMap#eventId2 sCache-aside + evict after commit
eventAvailability#eventId2 sCache-aside + evict after commit
  • Why 2 seconds. A stale seat map can never cause a double-booking — the index stops that. It only means a customer clicks a seat that just went and receives a 409. Seconds keeps that rare without hammering MySQL.
  • Evict, never write-through, and register it via TransactionSynchronization on afterCommit — otherwise a concurrent reader repopulates the cache with pre-commit state and the stale entry outlives the transaction.
  • Redis failure is survivable. CacheErrorHandler logs and falls through to MySQL with a 500 ms timeout.
Open risks

Cache errors are swallowed with no load shedding, so a Redis outage sends full read traffic to the primary. The fixed 2 s TTL also has no jitter, producing synchronised expiry bursts. Both need a circuit breaker and jittered TTLs before real load.

10 Layout editor

The admin app renders the hall as an interactive canvas — an SVG section overlay above absolutely positioned seat and table chips, plus a Three.js 3D view fed by the same snapshot.

PresetsNamed, server-persisted templates stamped into any hall
  • Everything is edited as unsaved drafts and persisted by a single PUT /api/halls/{id}/seats full-set reconcile — create, update and delete inferred by comparing sent ids against stored ones.
  • Seats are assigned to sections server-side by point-in-polygon containment, so the editor never has to maintain that relationship.
  • Deleting a section cascades to its price lines but is refused if it has bookings.

12 Running many instances

Most of the system is safe to replicate because its guarantees live in the database rather than in application memory. Three things needed fixing before a second instance was viable.

ConcernMechanismSafe across instances
Seat allocationUnique index on active_lockYes — enforced by the database
GA capacitySELECT … FOR UPDATE on the sectionYes
Rate limit & cacheRedis, sharedYes
Concurrent edits@VersionYes
RefundsClaim before calling the providerFixed — see below
Scheduled jobsRedis leaseFixed
Hold expiryDatabase-aligned clockFixed

Claiming a refund before issuing it

Deciding “a refund is owed” happens in a transaction; issuing it is a network call outside one. Previously the payment row was left INITIATED in between, so two replicas could both decide the same refund and both call the provider. On a single instance the same thing happened whenever the process died between refunding and recording it.

The claim is completed by markRefunded, which only accepts a row it owns; a worker that dies mid-refund leaves the row in REFUND_PENDING, which the reconciliation queue picks up and resumes rather than duplicating.

One instance per tick

SchedulerLease uses SET key owner NX PX ttl — atomic in Redis — with a TTL just under the schedule interval. It is never renewed or released early: it simply expires, so a worker that dies blocks the job for at most one interval and no cleanup path can leave a permanent lock behind.

The lease is an optimisation, not the guarantee

It fails open: if Redis is unreachable the job runs anyway. Duplicate work is wasteful but not incorrect — the sweeper is idempotent and refunds are claimed in the database. Failing closed would stop refunds and hold cleanup during a cache outage, which is worse.

Agreeing what time it is

Expiry is judged against expires_at, a value the database owns. If each replica used its own system clock, skew would let one instance release a hold while another still considered it live — and took payment for it.

DatabaseAlignedClock replaces the injected Clock, so every existing clock.instant() call site is corrected with no change at the call site. It samples SELECT CURRENT_TIMESTAMP(6) once a minute and applies the resulting offset locally, keeping the hot booking path free of a round trip. The sample subtracts half the query latency so a slow reading does not bias time forward, and an offset beyond five minutes is rejected as noise with a warning to check NTP.

13 High-demand on-sales

Seated booking is lock-free and shards naturally across seats, so it scales. The pressure points are the cache and the general-admission lock.

Cache stampede

With a fixed TTL every entry written during a burst expires in the same instant, and the next wave of readers all miss together — the exact load the cache exists to prevent, arriving on a timer. Two changes:

  • Jittered lifetimes. Each entry gets the configured TTL ±20%, spreading expiry across a window instead of concentrating it on one tick.
  • Single-flight. @Cacheable(sync = true) collapses a burst of concurrent misses for the same event into one loader call per instance, so a miss costs N queries rather than one per waiting request.

Connection pool

The Hikari default of 10 was a hard concurrency ceiling: general-admission booking holds a row lock for the length of its transaction, so a burst could occupy every connection while request threads queued behind them. Now sized explicitly, with a 3-second acquisition timeout so requests fail fast rather than deepening the backlog, and leak detection to surface a connection held longer than any legitimate transaction needs.

Budget is per instance

maximum-pool-size × replicas must stay well under MySQL's max_connections (151 by default). Scaling out and scaling the pool are the same budget spent twice.

Shortening the GA critical section

Capacity has no per-ticket identity, so no constraint can express “sum ≤ capacity” — the count and the insert must be serialised against each other. That lock is the throughput ceiling for a section, so everything that does not need to be consistent with it now happens before the lock is taken:

Why not a maintained counter

A sold_units column updated by one atomic conditional statement would shorten the critical section further, to microseconds. It was not taken: the counter would have to be decremented correctly on every cancel, lazy expiry, sweep and refund, and a counter that drifts oversells silently — strictly worse than a lock that is merely slow. Worth revisiting only with measurements showing this is the binding constraint.

Still open

  • All reads go to the primary; there is no replica routing, so browsing competes with selling.
  • No waiting room or queue — a stampede reaches the application tier in full.
  • A seat-map cache miss is O(seats + active holds); very large halls would benefit from paginating by section.
